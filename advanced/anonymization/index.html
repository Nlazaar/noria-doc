    Anonymisation RGPD / DCP

    Noria intègre un moteur d'anonymisation natif qui s'applique directement en SQL sur la table cible, après chaque écriture. Aucune dépendance externe, compatible avec tous les dialectes.

    Configuration

    Ajoutez anonymize: dans la définition d'un job :

    jobs:
  load_customers:
    sql: sql/load_customers.sql
    target: main.customers
    write_mode: replace
    anonymize:
      email:   hash      # pseudonymisation MD5
      phone:   mask      # "06 12 ** ** 78"
      nom:     partial   # "Ali***"
      ssn:     sha256    # hash SHA-256 (fort)
      adresse: redact    # → NULL
      salaire: noise     # valeur ±10% aléatoire

    Méthodes disponibles

    Méthode Résultat Usage typique
    hash MD5 32 chars, déterministe email, identifiant métier
    sha256 SHA-256 64 chars, plus fort IBAN, numéro sécu, mot de passe
    mask "Al***nt" — garde 2 chars début+fin téléphone, carte bancaire
    partial "Ali***" — garde 3 premiers + *** nom, prénom
    redact NULL — suppression totale adresse, données sensibles brutes
    noise valeur ± 10% aléatoire (numérique) salaire, âge, revenus

    Déterminisme

    hash et sha256 sont déterministes : la même valeur en entrée donne toujours le même hash. C'est une pseudonymisation (RGPD Art. 4-5), pas une anonymisation complète. Pour une anonymisation irréversible, utilisez redact.

    Comportement

    • L'anonymisation s'applique après l'écriture en table — le SQL source reste inchangé.
    • Compatible avec tous les modes d'écriture (replace, append, merge, …).
    • Les valeurs NULL restent NULL (aucune erreur).
    • Le nombre de colonnes anonymisées est loggé : 
      INFO  Tâche 'load_customers' — 3 colonne(s) anonymisée(s) dans 'main.customers'

    Combinaison avec les schema tests

    L'anonymisation est appliquée avant les schema tests, donc les vérifications portent sur les données masquées :

    jobs:
  load_customers:
    sql: sql/load_customers.sql
    target: main.customers
    anonymize:
      email: hash
    schema_tests:
      - column: email
        type: not_null   # vérifie que le hash n'est pas NULL

    Compatibilité dialectes

    Méthode DuckDB PostgreSQL BigQuery Snowflake
    hash ✓ MD5() ✓ MD5() ✓ TO_HEX(MD5()) ✓ MD5()
    sha256 ✓ sha256() ✓ digest() ✓ TO_HEX(SHA256()) ✓ SHA2()
    mask ✓ ✓ ✓ ✓
    partial ✓ ✓ ✓ ✓
    redact ✓ ✓ ✓ ✓
    noise ✓ random() ✓ random() ✓ RAND() ✓ UNIFORM()

    Exemple complet — pipeline RGPD

    # noria.yml
jobs:

  load_raw:
    sql: sql/load_raw.sql
    target: raw.customers_raw
    write_mode: replace
    description: "Chargement brut sans anonymisation (zone confidentielle)"

  anonymize_for_analytics:
    sql: sql/select_all_customers.sql   # SELECT * FROM raw.customers_raw
    target: analytics.customers
    write_mode: replace
    after: [load_raw]
    description: "Version anonymisée pour les équipes analytiques"
    anonymize:
      email:          hash
      phone:          mask
      date_naissance: noise
      adresse:        redact
      prenom:         partial
      nom_famille:    partial
    schema_tests:
      - column: email
        type: not_null
      - column: customer_id
        type: unique

    Bonnes pratiques RGPD

    Architecture recommandée

    • Zone brute (raw.*) : données originales, accès restreint
    • Zone analytique (analytics.*) : données anonymisées, accès élargi
    • Séparez les deux pipelines avec des after: pour garantir l'ordre

    Pseudonymisation vs anonymisation

    hash et sha256 sont réversibles avec un dictionnaire de correspondance. Pour une anonymisation complète au sens RGPD, préférez redact ou noise.

    Audit

    Chaque run loggue les colonnes anonymisées. La table d'audit _noria_audit enregistre le job, les métadonnées et l'horodatage — traçabilité complète.
