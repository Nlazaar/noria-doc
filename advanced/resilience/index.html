    Résilience et détection d'anomalies

    Noria propose deux mécanismes pour rendre les pipelines robustes face aux erreurs transitoires et aux données aberrantes :

    1. Retry ciblé — réessayer un job uniquement sur certains types d'erreurs
    2. Détection d'anomalies — alerter si le volume de données sort de la norme historique

    Retry ciblé (retry_on)

    Configuration de base

    jobs:
  load_api:
    sql: sql/load_api.sql
    target: main.api_data
    retry: 3              # jusqu'à 3 tentatives supplémentaires
    retry_delay_s: 10     # attendre 10s entre chaque tentative

    Avec retry seul, Noria réessaie sur n'importe quelle erreur.

    Filtrer par type d'erreur

    retry_on limite les retries aux erreurs dont le message contient l'un des motifs :

    jobs:
  load_api:
    sql: sql/load_api.sql
    target: main.api_data
    retry: 3
    retry_delay_s: 10
    retry_on:
      - "connection refused"
      - "timeout"
      - "too many connections"

    Si l'erreur est "SSL certificate expired" (absent de retry_on), Noria échoue immédiatement sans retenter — évitant d'attendre inutilement.

    Cas d'usage typiques

    Contexte Motifs retry_on
    API externe instable "timeout", "connection refused", "503"
    Base PostgreSQL sous charge "too many connections", "deadlock"
    BigQuery quota "rateLimitExceeded", "quota"
    Fichier source temporairement absent "file not found", "no such file"

    Erreurs non-retriables

    Les erreurs de logique SQL (syntax error, column not found, permission denied) ne doivent pas figurer dans retry_on — elles reflètent un problème de code, pas un problème transitoire.

    Détection d'anomalies de volume

    Noria compare le nombre de lignes écrites à l'historique des runs précédents via un z-score statistique. Si le volume sort trop de la normale, le job peut être mis en erreur ou générer un avertissement.

    Configuration

    jobs:
  load_orders:
    sql: sql/load_orders.sql
    target: main.orders
    anomaly_detection:
      enabled: true
      z_score_threshold: 3.0   # seuil par défaut
      min_history: 5           # runs historiques minimum pour activer
      warn_only: false         # false = erreur bloquante, true = warning

    Paramètres

    Paramètre Défaut Description
    enabled true Activer la détection pour ce job
    z_score_threshold 3.0 Seuil z-score au-delà duquel c'est une anomalie
    min_history 5 Nombre minimum de runs passés avant activation
    warn_only false true = log warning, false = erreur bloquante

    Comportement

    Une fois min_history runs enregistrés :

    Moyenne historique : 50 000 lignes
Écart-type : 2 000 lignes
Run actuel : 200 000 lignes → z-score = 75 → ANOMALIE

    Si warn_only: false (défaut) : 

    ExecutionError: Anomalie détectée pour 'load_orders' : 200 000 lignes
(z-score 75.0 > seuil 3.0, historique moy=50000, σ=2000)

    Si warn_only: true : 

    WARNING  Anomalie pour 'load_orders' : 200 000 lignes (z-score 75.0)
    Le pipeline continue malgré l'anomalie.

    Cas particulier — historique stable

    Quand tous les runs précédents ont exactement le même nombre de lignes (écart-type = 0), tout écart est considéré comme une anomalie :

    Historique : toujours 1 000 lignes
Run actuel : 1 ligne → ANOMALIE (valeur hors de la baseline stable)

    Stratégie recommandée

    jobs:
  load_critical:
    anomaly_detection:
      enabled: true
      z_score_threshold: 4.0   # tolérance plus large pour les tables volatiles
      min_history: 10
      warn_only: false         # bloquant — cette table alimente le reporting

  load_volatile:
    anomaly_detection:
      enabled: true
      z_score_threshold: 5.0   # données très variables (campagnes marketing)
      min_history: 20
      warn_only: true          # non-bloquant — surveiller sans stopper

    Combinaison retry + anomaly

    Ces deux mécanismes sont indépendants et se combinent naturellement :

    jobs:
  load_orders:
    sql: sql/load_orders.sql
    target: main.orders
    retry: 2
    retry_delay_s: 30
    retry_on:
      - "connection timeout"
    anomaly_detection:
      enabled: true
      z_score_threshold: 3.0
      warn_only: true
    1. Si la connexion échoue → retry jusqu'à 2 fois
    2. Une fois les données écrites → vérification du volume
    3. Si volume anormal → warning (pipeline continue)

    Timeout par job

    Pour éviter qu'un job bloquant ne fige tout le pipeline :

    jobs:
  load_slow_api:
    sql: sql/load_api.sql
    timeout: 300   # secondes — fail après 5 minutes
    retry: 1
    retry_on:
      - "timeout"
    Champ Description
    timeout Durée max en secondes (None = pas de limite)
    retry Nombre de retries après la première tentative
    retry_delay_s Délai entre retries (en secondes, accepte décimaux)
    retry_on Liste de motifs — retry seulement si l'erreur correspond
