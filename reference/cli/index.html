    Référence CLI

    noria run

    Lance le pipeline complet ou un sous-ensemble de jobs.

    noria run [OPTIONS]
    Option Description Défaut
    --job / -j Job(s) spécifiques à exécuter tous
    --env / -e Environnement (envs/{env}.yml) aucun
    --dry-run Compiler le SQL sans exécuter false
    --workers / -w Threads parallèles max 4
    --only-tags Filtre par tag(s) aucun
    --continue-on-error Ne pas s'arrêter sur erreur false
    --param k=v Paramètre CLI (surcharge noria.yml) aucun
    --params-file Fichier YAML de paramètres aucun
    --log-file Chemin du fichier de log aucun
    --monitor Démarrer le dashboard de monitoring false
    --fail-on-warning Code 3 si un job est en warning false
    --resume Reprendre un run précédent (run_id ou préfixe 8 chars). Incompatible avec --job et --param. aucun
    --verbose / -v Logs DEBUG détaillés false 
    noria run                              # tout exécuter (env défaut)
noria run --env prod                   # environnement prod
noria run --job clients                # un seul job
noria run --job clients --job rapport  # plusieurs jobs
noria run --only-tags daily            # jobs tagués daily
noria run --dry-run                    # SQL sans exécution
noria run --param schema=staging       # surcharge un paramètre
noria run --fail-on-warning            # exit 3 si warning
noria run --resume abc12345            # reprendre un run échoué

    Avec --job ou --only-tags, seuls les jobs choisis sont exécutés, sans attendre leurs dépendances non sélectionnées (elles ne sont pas relancées : leurs tables doivent déjà exister, et les valeurs d'un job compute_params non choisi ne sont pas calculées). L'ordre entre jobs choisis est conservé, même s'ils ne sont reliés que par un job non choisi (-j load -j report avec load → transform → report : report attend load). Si aucun job n'est exécuté (jobs désactivés, aucun tag ne correspond), le code retour est 1, avec un message. noria run-job <job> suit la même règle.

    Codes retour

    Code Signification
    0 Run OK (y compris avec des jobs en warning, sans --fail-on-warning)
    1 Au moins un job en échec (finished_ko)
    2 Erreur de configuration ou de connexion — aucun job lancé
    3 Run en warning avec --fail-on-warning

    Reprise d'un run échoué (--resume)

    noria run --resume <run_id>
noria run --resume abc12345   # préfixe 8 chars suffit

    --resume reprend un run précédent en ignorant les jobs déjà réussis. Utilisez noria status pour retrouver un run_id.

    Comportement :

    • Les jobs dont le statut était finished_ok, warning, skipped ou deactivated sont ignorés (statut skipped dans le nouveau run).
    • Les jobs en échec (finished_ko) ou avortés (aborted) sont rejoués normalement.
    • Les paramètres (--param, run_date…) du run d'origine sont automatiquement réutilisés.
    • Un job compute_params déjà réussi n'est pas relancé : ses valeurs sont rechargées depuis le run d'origine (relancé seulement pour un run enregistré par une version qui ne les conservait pas).
    • Incompatible avec --job et --param (exit 2).

    Statuts de job

    Statut Description
    waiting En attente que ses dépendances terminent
    running En cours d'exécution
    finished_ok Exécution réussie
    finished_ko Exécution échouée (au moins une tentative a échoué)
    warning Terminé avec des erreurs non bloquantes : itérations en échec avec foreach_on_error: continue, ou anomalie de volume détectée
    skipped Déclaré, non utilisé dans la version actuelle
    deactivated Job désactivé dans la configuration (active: false)
    aborted Non lancé : une de ses dépendances a échoué sans soft_fail ni --continue-on-error

    noria run-job

    Exécute un seul job sans ses dépendances.

    noria run-job <nom_du_job> [--env prod] [--dry-run]

    noria backfill

    Rejoue le pipeline une fois par jour entre --from et --to (inclus). Chaque run reçoit sa propre valeur de {{ run_date }}.

    noria backfill --from YYYY-MM-DD --to YYYY-MM-DD [OPTIONS]
    Option Description Défaut
    --from Date de début (YYYY-MM-DD, obligatoire) —
    --to Date de fin inclusive (YYYY-MM-DD, obligatoire) —
    --project / -p Répertoire du projet Noria .
    --env / -e Environnement (envs/{env}.yml) aucun
    --workers / -w Threads parallèles max par run 4
    --dry-run Compiler le SQL sans exécuter false
    --param k=v Paramètre CLI supplémentaire aucun
    --verbose / -v Logs DEBUG détaillés false 
    # Backfill sur 3 jours
noria backfill --from 2026-01-01 --to 2026-01-03

# Backfill en prod avec workers supplémentaires
noria backfill --from 2026-01-01 --to 2026-01-31 --env prod --workers 8

# Backfill d'un seul jour (--from == --to)
noria backfill --from 2026-06-15 --to 2026-06-15

    Comportement en cas d'échec d'un jour

    Si un jour échoue, le backfill continue sur les jours suivants et signale toutes les dates en erreur en fin de run. Le code retour est 1 si au moins un jour a échoué.

    ▶  2026-01-02
  ✗ 1 job(s) en échec.

▶  2026-01-03
  ✓ OK

✗ 1 run(s) en échec : 2026-01-02

    Avertissement append

    Si le pipeline contient des jobs en write_mode: append, un avertissement est affiché avant les runs :

    ⚠  Attention : les jobs suivants utilisent write_mode: append.
   Un backfill produira des doublons si des données existent déjà : <nom_du_job>

    Les jobs en append accumulent les données à chaque run — relancer N fois la même journée crée N fois les lignes. Préférer write_mode: replace ou truncate pour les backfills, ou s'assurer que les données sources sont déduplicables.

    noria schedule

    Lance le pipeline sur une planification cron. S'arrête avec Ctrl+C.

    noria schedule "0 6 * * *" [OPTIONS]

    L'argument positionnel est une expression cron à 5 champs : min heure jour-du-mois mois jour-de-la-semaine.

    Option Description Défaut
    --project / -p Répertoire du projet Noria .
    --env / -e Environnement (envs/{env}.yml) aucun
    --workers / -w Threads parallèles max par run 4
    --param k=v Paramètre CLI supplémentaire aucun
    --verbose / -v Logs DEBUG détaillés false 
    # Tous les jours à 6h
noria schedule "0 6 * * *"

# Toutes les heures en prod
noria schedule "0 * * * *" --env prod --workers 8

# Toutes les 30 minutes (via deux expressions) — non supporté nativement :
# utiliser deux processus ou un cron système avec noria run

    Détection des runs manqués

    Au démarrage, Noria compare l'heure actuelle au dernier déclenchement réussi enregistré dans tracking.db. S'il détecte des ticks cron manqués (arrêt du processus, redémarrage de la machine…), il les signale immédiatement :

    ⚠  2 run(s) manqué(s) depuis le dernier déclenchement :
   • 2026-01-02 06:00
   • 2026-01-03 06:00
   → Pour rattraper : noria backfill --from 2026-01-02 --to 2026-01-03

    Noria signale les runs manqués et indique la commande exacte — il ne les rejoue pas automatiquement. Copier-coller la suggestion noria backfill suffit pour récupérer les données.

    Premier démarrage

    Aucun avertissement n'est affiché au premier démarrage (aucun historique).

    noria jobs

    Liste tous les jobs du pipeline et leurs dépendances.

    noria jobs [--env prod]

    noria compile

    Compile le SQL Jinja2 sans exécuter — utile pour vérifier le SQL généré.

    noria compile [--job nom] [--env prod] [--output fichier.sql] [--param k=v]
    • Job foreach (liste statique) : le SQL de la 1re itération est affiché, précédé d'un en-tête qui l'indique (-- foreach : 1re itération sur 2 (cat=A) …). À l'exécution, chaque itération est compilée avec ses propres valeurs. Un --param qui porte le nom d'une variable de boucle ne change pas cet affichage, comme il ne change pas l'exécution.
    • Job foreach_query : les valeurs de boucle ne sont connues qu'à l'exécution. Une variable de boucle non fournie par --param est remplacée par _x_, et l'en-tête le signale.
    • --param suit le même ordre que noria run (voir Priorité des paramètres).

    noria test

    Exécute uniquement les jobs type: assert, sur des tables déjà alimentées (par un noria run précédent).

    noria test [--env prod] [--tag daily] [--param k=v]
    • Les asserts sont lancés sans attendre leurs after: : les jobs dont ils dépendent ne sont pas exécutés, leurs tables doivent déjà exister.
    • Un assert active: false est ignoré : il est affiché « désactivé » et ne fait pas échouer la commande.
    • Code retour 1 si au moins un assert échoue (y compris en statut warning : une itération en violation avec foreach_on_error: continue), ou si un assert actif n'a pas été exécuté : la liste est affichée avec leur statut.
    • Code retour 0 si chaque assert actif a été exécuté et a réussi.

    noria preview

    Affiche les premières lignes d'un job sans écrire en base.

    noria preview <nom_du_job> [--limit 20] [--env prod]

    noria validate

    Valide la configuration et le DAG sans connexion base de données.

    noria validate [--env prod] [--fail-on-warning]

    noria validate vérifie que les fichiers déclarés existent : sql:, chaque fichier de stages:, le seed_file d'un seed (sauf une URL https://, s3://…) et le file: de chaque hook (pre_hook, post_hook, on_failure_hook, foreach_pre_hook, foreach_post_hook). Un fichier absent donne le code retour 1, avec son chemin — sauf pour un hook en soft_fail: true : un avertissement (code 0, ou 3 avec --fail-on-warning), comme noria run, qui ignore ce hook avec un avertissement.

    En plus des erreurs de configuration, noria validate émet des avertissements : fichier absent d'un hook en soft_fail: true (ci-dessus), et dépendance non déclarée quand un job lit une table produite par un autre job sans le déclarer dans after:.

    Code retour Signification
    0 Configuration valide (avec ou sans avertissements)
    1 Erreur de configuration (ConfigError)
    3 Avertissements présents et --fail-on-warning actif

    Les noms de tables sont normalisés (casse ignorée, schéma par défaut ajouté : main pour DuckDB, public pour PostgreSQL) : customers et main.customers sont équivalents.

    ⚠  Le job 'monthly_report' lit 'main.customers', écrite par 'load_customers',
   sans le déclarer : ajoutez after: [load_customers].

    noria impact

    Analyse d'impact bidirectionnelle — sources/cibles d'un pipeline ou pipelines utilisant une table.

    noria impact [--pipeline nom] [--table schema.table] [--search motif]
    Option Description
    --pipeline Sources et cibles d'un pipeline donné
    --table Pipelines qui lisent/écrivent une table (accepte * en wildcard)
    --search Recherche par motif dans les noms de tables 
    noria impact                               # catalogue global de toutes les tables
noria impact --pipeline mon_pipeline       # impact d'un pipeline
noria impact --table analytics.customers  # impact d'une table
noria impact --table "raw.*"              # toutes les tables du schéma raw
noria impact --search customers           # tables contenant "customers"

    noria monitor

    Démarre le dashboard web de monitoring.

    noria monitor [--port 7070] [--host 127.0.0.1] [--open/--no-open]
    Option Description Défaut
    --port Port d'écoute 7070
    --host Interface d'écoute 127.0.0.1
    --open / --no-open Ouvrir automatiquement le navigateur --open
    --verbose / -v Logs DEBUG détaillés false 
    noria monitor                        # dashboard local sur http://127.0.0.1:7070
noria monitor --port 8080            # port personnalisé
noria monitor --no-open              # sans ouvrir le navigateur

    Sécuriser l'accès depuis un réseau distant

    Par défaut, le dashboard écoute uniquement sur 127.0.0.1 (loopback) et ne nécessite aucune authentification.

    Si vous devez l'exposer sur une interface accessible depuis le réseau (ex. --host 0.0.0.0), définissez la variable d'environnement NORIA_API_TOKEN avant de démarrer le serveur :

    export NORIA_API_TOKEN=<votre-secret>
noria monitor --host 0.0.0.0 --port 7070

    Sans ce token, le démarrage sur un hôte non-local est refusé.

    Les appels à POST /api/v1/runs devront alors inclure l'en-tête :

    Authorization: Bearer <votre-secret>

    Les routes de lecture (GET /api/v1/runs, dashboard HTML…) restent accessibles sans authentification.

    noria clean

    Supprime les tables de travail orphelines laissées par un run interrompu brutalement.

    noria clean [--yes]
    Option Description Défaut
    --yes / -y Supprimer sans confirmation (pour les ordonnanceurs) false 
    noria clean          # liste les tables et demande confirmation
noria clean --yes    # supprime directement (mode script)

    Fonctionnement

    Pendant un run, Noria crée des tables de travail nommées _noria_<job>_s<n>_<run_id>. Elles sont normalement supprimées à la fin de chaque job, mais un arrêt brutal (kill -9, crash) peut en laisser dans la base.

    noria clean :

    1. liste toutes les tables _noria_* présentes dans la base ;
    2. protège celles qui appartiennent à un run encore en cours (vérifié dans tracking.db — par PID sur la machine locale, par précaution sur une machine distante) ;
    3. affiche les tables orphelines, puis demande confirmation avant de les supprimer.
    3 table(s) de travail orpheline(s) :
  • main._noria_clients_s1_3f2a1b4c
  • main._noria_clients_s2_3f2a1b4c
  • main._noria_rapport_s1_3f2a1b4c

Supprimer ces tables ? [y/N]:

    Bases en réseau

    Sur une base distante, noria clean ne peut pas vérifier si le PID distant est encore vivant. Il protège par précaution toutes les tables dont le hostname ne correspond pas à la machine locale — elles n'apparaissent pas dans la liste.

    noria init

    Crée un nouveau projet Noria de façon interactive. La commande pose quelques questions, génère toute l'arborescence et affiche les étapes suivantes.

    noria init mon_pipeline

    Mode interactif (défaut)

    Noria Init — new project wizard

Database dialect
  1  duckdb         local file, zero config — ideal for development
  2  postgresql     standard SQL server
  3  bigquery       Google Cloud data warehouse
  4  snowflake      Snowflake cloud data warehouse

Choice [1-4]: 2
Default schema [main]: reporting
Include example SQL files? [Y/n]: Y
Run git init? [y/N]: y

    Noria génère ensuite l'arborescence complète et affiche les commandes suivantes :

    mon_pipeline/
├── noria.yml
├── envs/
│   ├── dev.yml
│   └── prod.yml
├── sql/
│   ├── macros/
│   │   └── utils.sql.j2
│   ├── 01_load_customers.sql
│   └── report/
│       ├── 01_aggregate.sql
│       └── 02_enrich.sql
└── README.md

    Options

    Option Description Défaut
    --dialect Dialecte : duckdb | postgresql | bigquery | snowflake prompt
    --schema Schéma par défaut prompt (main ; public sous PostgreSQL)
    --minimal Structure vide sans exemples SQL false
    --git / --no-git Lancer git init après création false
    --yes / -y Mode non-interactif (pas de prompts, valeurs par défaut) false
    --dir / -d Dossier parent répertoire courant

    Mode non-interactif (CI/scripts)

    # Projet DuckDB complet, tout en une ligne
noria init mon_pipeline --dialect duckdb --schema main --yes

# Projet PostgreSQL sans exemples
noria init mon_pipeline --dialect postgresql --schema reporting --minimal --yes

# Projet avec git init automatique
noria init mon_pipeline --dialect duckdb --git --yes

    noria.yml généré selon le dialecte

    Chaque dialecte produit un noria.yml et des envs/ préconfigurés :

    === "DuckDB"

    ```yaml
database:
  dialect: duckdb
  database: .noria/data.db
```

    === "PostgreSQL"

    ```yaml
database:
  dialect: postgresql
  host: ${DB_HOST}
  port: 5432
  user: ${DB_USER}
  password: ${DB_PASSWORD}
  database: ${DB_NAME}
```

    === "BigQuery"

    ```yaml
database:
  dialect: bigquery
  project: ${GCP_PROJECT}
  dataset: main
  credentials_path: ${GOOGLE_APPLICATION_CREDENTIALS}
```

    === "Snowflake"

    ```yaml
database:
  dialect: snowflake
  account: ${SNOWFLAKE_ACCOUNT}
  user: ${SNOWFLAKE_USER}
  password: ${SNOWFLAKE_PASSWORD}
  database: ${SNOWFLAKE_DATABASE}
  warehouse: ${SNOWFLAKE_WAREHOUSE}
```

    Utilisation avec un ordonnanceur

    Noria est conçu pour s'intégrer sans friction dans Jenkins, Airflow, cron ou tout autre ordonnanceur.

    # Jenkins / script shell
noria run --env prod --project /pipelines/mon_pipeline --log-file logs/run.log

# Airflow (BashOperator)
noria run --env prod --only-tags daily --continue-on-error

# Cron (crontab)
0 6 * * * cd /pipelines/mon_pipeline && noria run --env prod

    Les variables de connexion sensibles passent par des variables d'environnement résolues dans envs/prod.yml :

    # envs/prod.yml
database:
  host: ${DB_HOST}
  password: ${DB_PASSWORD}
