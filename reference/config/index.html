    Configuration — noria.yml

    Le fichier noria.yml est la configuration centrale de tout projet Noria. Il décrit la base de données, les sources de données, les paramètres globaux, et l'ensemble des jobs du pipeline.

    Structure complète

    name: mon_pipeline                  # (requis) identifiant du pipeline
description: "Description courte"  # (optionnel)
version: "1"                        # (optionnel) version du pipeline

database:
  dialect: duckdb                   # duckdb | postgresql | bigquery
  database: .noria/data.db
  host: localhost                   # PostgreSQL uniquement
  port: 5432
  user: mon_user
  password: "${DB_PASSWORD}"        # supporte ${ENV_VAR}
  schema: mon_schema

params:
  schema: main
  annee: 2024

params_file: params/extra.yml       # fichier YAML de params supplémentaires
macros_dir: sql/macros              # répertoire des macros Jinja2 utilisateur
tracking_db: .noria/tracking.db     # base SQLite de suivi des exécutions

monitoring:
  enabled: false
  host: 127.0.0.1
  port: 7070
  auto_open: false

notifications:
  on_failure:
    - "https://hooks.slack.com/services/xxx"
    - "email:ops@mycompany.com"
  on_success: []
  timeout_s: 10

# Catalog : déclarez vos sources une fois, référencez-les partout
catalog:
  raw_clients:
    schema: raw
    table: customers
    description: "Clients source"
  raw_orders: "raw.orders"           # notation courte acceptée

# Schemas : SQL non qualifié, Noria route automatiquement vers schema.table
schemas:
  staging:
    - raw_orders
    - raw_clients
  dwh:
    - dim_client
    - "dim_client as edd_dim"        # alias si doublon de nom entre schémas

jobs:
  nom_job:
    # ... voir référence ci-dessous

    Section database

    Champ Type Défaut Description
    dialect string duckdb Moteur : duckdb, postgresql, bigquery
    database string :memory: Chemin fichier DuckDB, nom BDD PostgreSQL, ou project ID BigQuery
    host string — Hôte PostgreSQL
    port int — Port (défaut PostgreSQL : 5432)
    user string — Utilisateur
    password string — Mot de passe — utiliser ${ENV_VAR} ou .noria/.env
    schema string — Schéma par défaut

    Section catalog

    Le catalog permet de déclarer les tables sources une seule fois et de les référencer dans tous les SQL via {{ source('id') }}.

    catalog:
  raw_clients:
    schema: raw
    table: customers
    description: "Table clients brute"
  raw_orders: "raw.orders"     # shorthand : "schema.table"
  ref_regions:
    schema: ref
    table: regions

    -- Dans n'importe quel fichier SQL du projet
SELECT * FROM {{ source('raw_clients') }}
-- → compile en : SELECT * FROM raw.customers

    Changer de schéma sans toucher au SQL

    Si vos données sources changent de schéma (migration, environnement), modifiez uniquement le catalog — tous les SQL s'adaptent automatiquement.

    Section schemas:

    Le bloc schemas: permet d'écrire du SQL pur non qualifié — sans préfixe schéma ni syntaxe Jinja2 — et de laisser Noria qualifier automatiquement les noms de tables à la compilation.

    schemas:
  staging:
    - raw_orders
    - raw_clients
  dwh:
    - dim_client
    - fact_ventes
    - "dim_client as edd_dim"   # alias si même nom dans un autre schéma

    -- Ce que vous écrivez
SELECT * FROM raw_orders o JOIN dim_client d ON o.client_id = d.id

-- Ce que Noria exécute
SELECT * FROM staging.raw_orders o JOIN dwh.dim_client d ON o.client_id = d.id

    Règles clés :

    • Les tables déjà qualifiées (staging.raw_orders), les fonctions tabulaires (read_csv()), les CTEs et les commentaires sont automatiquement ignorés.
    • Si schemas: est défini et qu'une table n'est pas dans le mapping → SchemaResolutionError à la compilation.
    • Si schemas: est absent → aucune modification (compatibilité totale avec les projets existants).
    • En cas de doublon de nom (même table dans deux schémas), utilisez "table as alias" pour disambiguïser.

    Documentation complète

    Voir la page dédiée schemas: pour les exemples d'alias, l'interaction avec catalog:, stages:, les CTEs, et les messages d'erreur.

    Section params

    Paramètres globaux accessibles dans tous les SQL via {{ params.nom }} ou directement {{ nom }}.

    params:
  date_from: "2024-01-01"

schemas:
  main:
    - commandes

    -- Le schéma est géré par schemas: — plus besoin de {{ params.schema }} dans le SQL
SELECT * FROM commandes
WHERE date_op >= '{{ params.date_from }}'

    Priorité des paramètres (du plus faible au plus fort)

    1. params: dans noria.yml
    2. params_file: (fichier YAML externe)
    3. envs/{env}.yml (overlay d'environnement)
    4. params: au niveau du job
    5. --param k=v en CLI

    Environnements (envs/)

    Les fichiers envs/*.yml permettent de surcharger la config de base selon l'environnement, sans toucher noria.yml.

    mon_pipeline/
├── noria.yml          # config commune (DuckDB local par défaut)
└── envs/
    ├── dev.yml        # développement
    └── prod.yml       # production

    # envs/prod.yml — surcharge uniquement ce qui change
database:
  dialect: postgresql
  host: ${DB_HOST}
  port: 5432
  user: ${DB_USER}
  password: ${DB_PASSWORD}
  database: ${DB_NAME}
params:
  schema: prod

    noria run              # utilise noria.yml (DuckDB local)
noria run --env prod   # merge envs/prod.yml sur noria.yml

    Deep merge

    L'overlay est fusionné récursivement : seules les clés définies dans envs/prod.yml surchargent noria.yml. Le reste est hérité.

    Champs d'un job

    Identification

    Champ Type Défaut Description
    type string sql Type : sql, assert, seed
    sql string — Chemin du fichier SQL (incompatible avec stages:)
    stages list — Liste de fichiers SQL chaînés (incompatible avec sql:)
    target string — Table cible schema.table (Jinja2 compilé)
    description string — Description du job
    active bool true Désactiver sans supprimer
    tags list [] Tags pour filtrage CLI (--only-tags)

    Chargement

    Champ Type Défaut Description
    write_mode string replace Stratégie d'écriture (voir Modes d'écriture)
    merge_key list — Clés pour merge
    incremental_key string — Colonne de partition pour incremental
    safe_replace_min_rows int 1 Seuil minimum de lignes pour safe_replace
    scd2_key list — Clé métier pour scd2
    update_key list — Clés de recherche pour update
    update_cols list — Colonnes à mettre à jour (toutes si absent)

    Résilience

    Champ Type Défaut Description
    retry int 0 Nombre de réessais
    retry_delay_s float 0.0 Secondes entre les réessais
    timeout int — Timeout en secondes
    soft_fail bool false Ne pas bloquer le pipeline si échec
    always_run bool false Exécuter même si une dépendance a échoué

    Dépendances

    Champ Type Défaut Description
    after list [] Jobs qui doivent terminer avant celui-ci
    params dict {} Paramètres locaux (surchargent les params globaux)

    Hooks

    pre_hook:
  file: sql/hooks/avant.sql
  soft_fail: false   # true = log l'erreur mais continue
post_hook:
  file: sql/hooks/apres.sql
  soft_fail: true

    Seeds

    Champ Type Défaut Description
    seed_file string — Chemin du fichier (CSV, Parquet, JSON)
    seed_delimiter string , Séparateur CSV
    seed_encoding string utf-8 Encodage
    seed_null_value string "" Valeur considérée comme NULL

    Freshness check

    freshness_check:
  column: updated_at   # colonne timestamp
  max_hours: 24        # échoue si plus vieux que 24h

    Stages — enchaîner plusieurs SQL dans un job

    Les stages permettent de décomposer un job complexe en plusieurs fichiers SQL exécutés en séquence. Chaque étape intermédiaire est matérialisée en table temporaire, accessible dans l'étape suivante via {{ prev }}.

    jobs:
  rapport_mensuel:
    stages:
      - sql/report/01_extract.sql      # stage 1
      - sql/report/02_transform.sql    # stage 2 — utilise {{ prev }}
      - sql/report/03_format.sql       # stage final — écrit dans target
    target: "{{ params.schema }}.rapport"
    write_mode: replace

    -- sql/report/01_extract.sql
SELECT client_id, SUM(montant) AS total
FROM {{ source('raw_orders') }}
GROUP BY client_id

    -- sql/report/02_transform.sql
-- {{ prev }} = table temporaire créée par le stage précédent
SELECT
    client_id,
    total,
    CASE WHEN total > 1000 THEN 'premium' ELSE 'standard' END AS segment
FROM {{ prev }}

    -- sql/report/03_format.sql
SELECT *, {{ current_timestamp() }} AS computed_at
FROM {{ prev }}
ORDER BY total DESC

    Règles des stages

    • sql: et stages: sont mutuellement exclusifs
    • Seul le dernier stage est écrit dans target:
    • Les stages intermédiaires sont des tables temporaires de session (non persistées)
    • {{ prev }} vaut NULL dans le premier stage (aucune étape précédente)

    compute_params: — jobs calculateurs

    Un job avec compute_params: true exécute un SELECT sans écrire en base. La première ligne du résultat est injectée comme paramètres dans tous les jobs suivants (ceux déclarés avec after:).

    jobs:
  # Job calculateur — pas de target
  calcul_seuils:
    sql: sql/calcul_seuils.sql
    compute_params: true           # la première ligne devient des params

  # Jobs suivants — voient {{ params.date_max }}, {{ params.seuil_ca }}
  rapport_ventes:
    sql: sql/rapport_ventes.sql
    target: "{{ params.schema }}.rapport_ventes"
    write_mode: replace
    after: [calcul_seuils]

  rapport_clients:
    sql: sql/rapport_clients.sql
    target: "{{ params.schema }}.rapport_clients"
    write_mode: replace
    after: [calcul_seuils]

    -- sql/calcul_seuils.sql — retourne 1 ligne, colonnes = noms des params
SELECT
    MAX(date_op)            AS date_max,
    MIN(date_op)            AS date_min,
    ROUND(AVG(montant), 0)  AS seuil_ca,
    COUNT(DISTINCT region)  AS nb_regions
FROM main.commandes
WHERE statut = 'V'

    -- sql/rapport_ventes.sql — utilise les params injectés
SELECT region, SUM(montant) AS ca
FROM main.commandes
WHERE date_op BETWEEN '{{ params.date_min }}' AND '{{ params.date_max }}'
  AND montant >= {{ params.seuil_ca }}
GROUP BY region

    Règles

    • compute_params: true est incompatible avec target: et stages:
    • Si le SELECT retourne plusieurs lignes, seule la première est utilisée
    • Si le SELECT retourne zéro ligne, un warning est loggé et aucun param n'est injecté
    • Les valeurs NULL dans la ligne résultat sont ignorées (non injectées)
    • Les params injectés ont la même priorité que params: au niveau du job — ils peuvent être surchargés par --param key=value CLI

    Combinaison avec foreach

    Un job compute_params peut lui-même utiliser des {{ params.xxx }} provenant du YAML ou de la CLI — utile pour calculer des seuils dynamiques en fonction de la période passée par l'ordonnanceur.

    Section audit

    Après chaque job, Noria écrit automatiquement une ligne dans une table _noria_audit de la base cible. Cette table est créée à la première exécution si elle n'existe pas.

    audit:
  enabled: true            # activer/désactiver (défaut : true)
  schema: "{{ params.schema }}"  # schéma de la table d'audit (défaut : sans schéma)
  table: _noria_audit      # nom de la table (défaut : _noria_audit)
    Champ Défaut Description
    enabled true Écrire une ligne d'audit après chaque job
    schema — Schéma de la table d'audit (recommandé : même que params.schema)
    table _noria_audit Nom de la table d'audit

    Structure de la table d'audit

    Colonne Type Description
    run_id VARCHAR Identifiant de l'exécution du pipeline
    pipeline_name VARCHAR Nom du pipeline
    job_name VARCHAR Nom du job
    write_mode VARCHAR Mode d'écriture utilisé
    target VARCHAR Table cible
    start_time TIMESTAMP Heure de début du job
    end_time TIMESTAMP Heure de fin
    duration_s DOUBLE Durée en secondes
    rows_read BIGINT Lignes lues (0 si non disponible)
    rows_loaded BIGINT Lignes présentes dans la table cible après écriture
    status VARCHAR finished_ok, finished_ko, warning
    error_message TEXT Message d'erreur (NULL si succès) 
    -- Interroger l'historique d'audit directement en SQL
SELECT job_name, status, duration_s, rows_loaded, start_time
FROM main._noria_audit
ORDER BY start_time DESC
LIMIT 20;

    Désactiver l'audit

    audit:
  enabled: false

    Variables d'environnement

    Les valeurs ${NOM_VAR} sont résolues depuis .noria/.env (auto-chargé) puis le shell.

    # .noria/.env
DB_HOST=prod-postgres.example.com
DB_PASSWORD=secret123

    # noria.yml ou envs/prod.yml
database:
  host: ${DB_HOST}
  password: ${DB_PASSWORD}

    Rétrocompatibilité

    Les anciens noms de clés sont encore acceptés et remappés automatiquement :

    Ancienne clé Nouvelle clé
    tasks: / nodes: jobs:
    depends_on: / needs: after:
    write_mode: write_mode: (inchangé)
    loop: foreach:
    loop_from_query: foreach_query:
    output_write: write_mode:
