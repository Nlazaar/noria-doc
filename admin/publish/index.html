    Publier une nouvelle version de Noria sur PyPI

    Ce guide est destiné au mainteneur du package.

    La règle

    La publication est automatique et ne dépend que de la version déclarée dans pyproject.toml :

    Sur un push vers main, si la version de pyproject.toml n'existe pas encore sur PyPI, et si les tests sont verts (Python 3.10, 3.11 et 3.12), alors la CI publie le paquet sur PyPI et crée le tag vX.Y.Z. Sinon, elle ne fait rien.

    Le message de commit ne joue aucun rôle. Une version déjà publiée n'est jamais republiée.

    Changer la version = publier

    Ne modifiez la version de pyproject.toml que lorsque vous voulez réellement publier. Une fois fusionnée sur main, la publication part toute seule.

    Comment la CI vérifie la version

    Le job « Version à publier » (.github/scripts/version_a_publier.py) :

    1. lit version dans pyproject.toml et vérifie qu'elle est identique à __version__ dans src/noria/_version.py (sinon, échec) ;
    2. interroge l'API JSON de PyPI (« Get a release ») : GET https://pypi.org/pypi/noria/<version>/json :
      • 200 : la version existe déjà, rien à publier ;
      • 404 : la version n'existe pas encore, elle sera publiée ;
      • autre réponse, ou PyPI injoignable : échec, rien n'est publié.

    Sur une pull request, l'étape « Simulation (PR) » affiche seulement ce qui se passerait après la fusion : publierait X.Y.Z ou rien à publier. Rien n'est publié depuis une PR.

    Le job « Publish to PyPI » revérifie PyPI juste avant l'envoi (deux pushes rapprochés ne publient pas deux fois), construit le paquet (python -m build), le publie avec pypa/gh-action-pypi-publish en trusted publishing (OIDC, aucun token stocké), puis pousse le tag vX.Y.Z sur le commit publié.

    Publier une version

    1. Préparer une PR de release

    Sur une branche créée depuis main (ex. chore/release-0.6.0) :

    • changer la version dans pyproject.toml et dans src/noria/_version.py (même valeur) ;
    • compléter le CHANGELOG.md.

    Versionnage sémantique :

    Type de changement Exemple
    Correctif (bug fix) 0.5.0 → 0.5.1
    Nouvelle fonctionnalité (rétrocompatible) 0.5.0 → 0.6.0
    Rupture de compatibilité 0.5.0 → 1.0.0

    2. Vérifier la simulation

    Dans la CI de la PR, l'étape « Simulation (PR) » du job « Version à publier » doit afficher publierait 0.6.0.

    3. Fusionner

    Après la fusion dans main, la CI publie la version et crée le tag v0.6.0. Aucune autre action n'est nécessaire.

    4. Vérifier la publication

    pip index versions noria
git fetch --tags && git tag --list 'v*'

    Ou sur pypi.org/project/noria.

    En cas d'erreur

    Le job « Version à publier » échoue : versions différentes

    pyproject.toml et src/noria/_version.py ne déclarent pas la même version. Alignez-les.

    Le job « Version à publier » échoue : PyPI injoignable

    Erreur réseau ou réponse inattendue de PyPI. Relancez le job ; rien n'a été publié.

    Les tests échouent

    La publication ne part pas. Corrigez, puis poussez de nouveau sur main : la version étant toujours absente de PyPI, elle sera publiée au prochain push vert.

    « File already exists »

    PyPI n'accepte pas l'écrasement d'une version existante. Il faut changer la version.

    Publication manuelle (secours)

    Uniquement si la CI est indisponible. Il faut un token API PyPI limité au projet noria (PyPI : Account settings → API tokens).

    uv run python -m pytest
rm -rf dist/
uv build
uv publish --token pypi-XXXXXXXXXXXXXXXX
git tag vX.Y.Z && git push origin vX.Y.Z
